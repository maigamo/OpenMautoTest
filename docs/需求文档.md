OpenMautoTest 项目需求文档 (V1.0)
1. 项目概述
1.1 项目背景
随着业务的快速迭代，软件测试的复杂度和重复性日益增加。为了提高测试效率、保证产品质量并缩短发布周期，我们需要建立一个自动化、可度量、易于扩展的统一测试框架。OpenMautoTest 项目旨在构建一个集 Web 端（PC 浏览器）和 Mini 端（小程序）自动化测试于一体的解决方案，通过 CI/CD 工具（Jenkins）进行调度，并将测试结果进行持久化存储和数据可视化，从而为项目质量和效率改进提供数据支持。

1.2 项目目标
本项目 V1.0 的核心目标是搭建一个可运行的、端到端的自动化测试与度量 MVP (Minimum Viable Product，最小可行产品)。具体实现：

测试执行自动化：通过 Jenkins 创建并触发任务，自动执行 Web 和 Mini 程序的UI自动化测试流程。

测试框架集成：使用 Pytest作为测试执行引擎，集成 Playwright 驱动 Web 端测试。

结果报告生成：每次测试执行后，能够生成直观、易于分析的测试报告（如 Allure Report）。

数据持久化：将核心测试执行指标存储到设计良好的 PostgreSQL 数据库中。

数据可视化：在 Metabase 中配置并展示关键效能指标的仪表盘，实现对自动化测试历史数据的监控和分析。

1.3 目标用户
测试工程师 (QA)：编写和执行自动化测试用例，分析测试报告，定位问题。

开发工程师 (Dev)：在代码提交后，通过自动化测试快速获得质量反馈。

项目经理/团队主管 (PM/TL)：通过可视化仪表盘，直观了解项目的自动化水平、质量趋势和效率提升情况。

1.4 系统架构概述
OpenMautoTest 系统采用分层架构设计，主要包含以下核心组件：

**测试执行层**：基于 Pytest + Playwright(Web) + Minium(Mini程序) 的测试引擎
**流程编排层**：orchestrator 模块负责测试流程的调度和数据记录
**数据存储层**：PostgreSQL 数据库存储测试执行数据
**可视化层**：Metabase 提供数据分析和可视化
**CI/CD层**：Jenkins 负责任务调度和报告生成

1.5 前置条件与环境依赖
在开始使用 OpenMautoTest 之前，需要确保以下环境和依赖已准备就绪：

**基础环境要求**：
- Python 3.8+ 
- Node.js 16+ (用于小程序自动化)
- Docker & Docker Compose (用于数据库和可视化服务)
- Git (代码版本控制)

**外部服务依赖**：
- Jenkins 服务器 (CI/CD调度)
- PostgreSQL 数据库 (数据存储)
- Metabase 服务 (数据可视化)

**测试目标环境**：
- 可访问的Web应用环境
- 可调试的小程序环境或开发者工具

2. 功能性需求
2.1 持续集成与调度 (CI/CD)
FR-2.1.1 Jenkins 任务创建：

支持在 Jenkins 中创建 Pipeline 或 Freestyle 项目来运行 OpenMautoTest 测试。

Jenkins 任务应能从代码仓库（如 Git）拉取最新代码。

FR-2.1.2 Jenkins 任务触发：

支持手动触发 Jenkins 任务。

任务能够接收参数（如：指定运行的测试流程、目标环境等）。

FR-2.1.3 Jenkins 调用测试脚本：

Jenkins 任务需要能够正确安装项目依赖 (requirements.txt)。

任务核心步骤为执行 Makefile 中定义的 test 命令，该命令实质上是调用 pytest。

2.2 自动化测试执行
FR-2.2.1 测试框架：

使用 pytest 作为核心测试用例组织和执行框架。

FR-2.2.2 Web 端自动化：

使用 Playwright 作为 Web 端的浏览器驱动库，实现页面元素的定位与交互。

FR-2.2.3 Mini 端（小程序）自动化：

需集成小程序自动化驱动框架（如 minium），实现对小程序的自动化操作。

FR-2.2.4 跨端流程编排：

在 flows/ 目录下，能够定义一个完整的业务流程（如 login_and_buy），该流程可以包含多个 Web 端和 Mini 端的步骤。

**流程执行机制**：
- 每个 flow 包含 `web_steps.py` 和 `mini_steps.py` 两个步骤文件
- 通过 `orchestrator/flow_runner.py` 统一调度执行
- 支持步骤间数据传递和状态共享
- 支持条件分支和异常处理

FR-2.2.5 测试用例发现与执行：

**用例发现机制**：
- pytest 自动扫描 flows/ 目录下的 test_*.py 文件
- 支持通过标签 (markers) 过滤特定类型的测试用例
- 支持通过命令行参数指定执行范围

**执行顺序控制**：
- 使用 pytest-order 插件控制用例执行顺序
- 支持依赖关系定义，确保前置条件满足
- 失败用例不影响其他独立用例的执行

2.3 测试结果与报告
FR-2.3.1 过程截图：

在测试用例执行失败时，系统应能自动截取当前屏幕快照，并保存在 output/screenshots/ 目录下。

FR-2.3.2 Allure 报告生成：

pytest 运行时需集成 Allure 插件，将测试结果数据生成在 output/allure-results/ 目录。

Jenkins 任务执行完毕后，能够通过 Allure Jenkins 插件展示本次执行的详细测试报告。

2.4 数据采集与存储
FR-2.4.1 数据模型定义：

经过审查，为确保数据的完整性、可扩展性和查询性能，我们对数据表结构进行了优化设计。新增了主键、项目名、环境和重试次数字段，为当前和未来的数据分析提供更丰富的上下文。

核心数据表（建议命名为 test_case_runs）设计如下：

字段名 (Column)	类型 (Type)	约束 (Constraint)	描述 (Description)
id	BIGINT	PRIMARY KEY	唯一标识符，自增主键，确保每一条用例执行记录都有唯一的ID。
run_id	VARCHAR(255)	NOT NULL	单次任务ID。由CI/CD系统（如Jenkins的$BUILD_TAG）生成，用于关联同一次构建中的所有测试用例。
project_name	VARCHAR(100)		项目/团队名称。用于在多项目/团队共用平台时进行数据隔离和对比分析（为未来需求预留）。
flow_name	VARCHAR(255)		业务流程名称。对应 flows/ 下的目录名，如 login_and_buy。
test_case_name	TEXT	NOT NULL	测试用例名称。pytest 收集到的具体测试用例名，是分析失败用例TOP10的核心维度。
status	VARCHAR(20)	NOT NULL	执行结果。枚举值：passed, failed, skipped。
environment	VARCHAR(50)		测试环境。执行测试的目标环境，如 staging, production, dev。
start_time	TIMESTAMPTZ	NOT NULL	开始时间。用例执行的开始时间（含时区）。
end_time	TIMESTAMPTZ	NOT NULL	结束时间。用例执行的结束时间（含时区）。
duration	FLOAT		执行耗时（秒）。(end_time - start_time) 的差值，用于计算节省人时和性能趋势。
failure_reason	TEXT		失败原因。如果 status 为 failed，记录简明的错误信息或异常类型（如 AssertionError），避免存储完整堆栈。
retry_attempt	INTEGER	DEFAULT 0	重试次数。用于未来分析用例稳定性（首次成功率 vs 重试成功率），V1.0中该值恒为0。
jenkins_build_url	TEXT		构建链接。关联到触发本次测试的Jenkins构建页面，方便从报表快速追溯日志。

Export to Sheets
FR-2.4.2 数据写入：

在 orchestrator/recorder.py 模块中，实现将每次测试执行的记录写入到 PostgreSQL 的 test_case_runs 表中。

**数据流转机制**：
- 通过 pytest hooks (pytest_runtest_*) 收集测试执行数据
- 在 conftest.py 中配置全局 fixture 触发数据记录
- 使用 orchestrator/recorder.py 统一处理数据写入逻辑

**数据写入策略**：
- 采用批量写入模式提高性能，每批次最多100条记录
- 实现写入失败时的重试机制，最多重试3次
- 写入失败不影响测试执行，仅记录警告日志

**异常处理机制**：
- 数据库连接异常：自动重试连接，失败后降级到本地文件记录
- 数据格式异常：记录错误日志并跳过异常数据
- 磁盘空间不足：清理历史日志文件并告警

FR-2.4.3 配置管理：

**配置文件优先级**（从高到低）：
1. 环境变量 (DATABASE_URL, JENKINS_URL 等)
2. configs/settings.py 中的配置项
3. configs/*.yaml 配置文件
4. 代码中的默认值

**配置验证**：
- 启动时验证所有必需配置项
- 提供配置检查命令 `make check-config`
- 敏感信息（密码、密钥）支持环境变量注入

2.5 数据可视化 (Metabase)
FR-2.5.1 数据源连接：

Metabase 需预先配置好，并成功连接到存储测试数据的 PostgreSQL 数据库。

FR-2.5.2 核心指标看板 (V1.0)：

需要在 Metabase 中创建一个名为 "质量核心看板" 的仪表盘。

该仪表盘 V1.0 阶段必须包含以下图表：

历史自动化执行总数 (KPI)：一个数字卡片，显示自动化测试被触发的总次数。

历次自动化执行的测试用例数 (趋势图)：以时间为 X 轴，展示每次 Jenkins 构建所执行的测试用例总数。

测试用例成功率 (趋势图/饼图)：按天或按次统计自动化测试用例的整体成功率 (成功数 / 总数 * 100%)。

单次任务总耗时 (趋势图)：以时间为 X 轴，展示每次自动化任务的总执行时间。这个时间代表了通过自动化节省下来的人工测试时间。

节省人时累计曲线 (面积图)：按天累计所有 status 为 passed 的用例的 duration 总和。此图表直观展示了自项目开始以来，通过自动化测试累计节省的总工时，是衡量自动化 ROI (投资回报率) 的关键指标。

失败用例 TOP10 (横向条形图)：统计一段时间内（如最近30天），失败次数最多的 10 个测试用例 (test_case_name)。此图表有助于团队快速定位当前版本中最不稳定、问题最集中的功能点，为修复提供明确指引。

FR-2.5.3 看板初始化：

实现 metabase/init/automationOS_dashboard.json 的自动导入，当 Metabase 容器首次启动时，能够自动创建上述看板和图表。

3. 非功能性需求
NF-3.1 易用性：

工程师可以通过 Makefile 中的简单命令（如 make test）在本地快速运行测试。

README.md 文档需提供清晰的快速开始指南。

**用户体验要求**：
- 提供命令行帮助信息 `--help` 选项
- 测试执行过程中显示进度条和实时状态
- 失败时提供明确的错误信息和解决建议

NF-3.2 可靠性：

Jenkins 任务的执行状态应能准确反映测试结果（成功或失败）。

数据库连接应具备重试和异常处理机制，确保数据记录的稳定性。

**故障恢复机制**：
- 网络异常时自动重试，最多重试3次
- 测试超时机制：单个用例最长执行时间5分钟
- 资源清理：测试结束后自动关闭浏览器和清理临时文件
- 健康检查：提供系统组件状态检查接口

NF-3.3 可扩展性：

整体架构及数据模型的设计应支持未来轻松添加新的测试流程、页面对象以及新的数据分析维度。

**扩展性设计**：
- 插件化架构支持新的测试驱动器接入
- 数据表结构预留扩展字段
- 配置文件支持环境特定覆盖
- API接口设计支持版本兼容

NF-3.4 可维护性：

代码遵循 Python 编码规范（PEP8）。

配置文件（如 db.yaml, settings.py）应与业务逻辑代码分离，便于修改和管理。

**代码质量要求**：
- 单个代码文件不超过500行，超过需拆分
- 函数复杂度不超过10 (McCabe complexity)
- 强制类型提示 (Type Hints)

5. 风险与约束
5.1 技术风险
**小程序自动化风险**：
- 小程序调试工具的稳定性可能影响测试执行
- 微信开发者工具版本更新可能导致兼容性问题
- 缓解措施：提前验证工具兼容性，准备降级方案

**数据一致性风险**：
- 并发写入可能导致数据冲突
- 缓解措施：使用数据库事务和乐观锁机制

5.2 业务约束
**测试环境约束**：
- 测试环境必须稳定可用，停机维护需提前通知
- 测试数据需要定期重置和清理

**资源约束**：
- Jenkins 执行器数量限制并发任务数
- 数据库存储空间需要定期监控和扩容
